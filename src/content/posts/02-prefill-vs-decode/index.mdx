In Post 1, a prompt went through two phases: prefill (the prompt phase), then decode (one token at a time).

Here is what each one looks like on the H100, measured at batch 1:

Prefill: 512 prompt tokens in 54 ms

- 0.1 ms per token
- \~460 TFLOP/s: 46% of the H100's 989 TFLOP/s
- memory: 0.94 TB/s, 28% of the 3.35 TB/s
- compute-bound

Decode: 1 new token in 20.6 ms

- 20.6 ms per token, \~190x more than prefill
- 2.5 TFLOP/s: 0.25% of peak
- memory: 2.49 TB/s, 74% of peak
- memory-bound

Why? Every token has to "see" all the weights: 51.2 GB of them (25.6B parameters in BF16).

- Prefill reads those 51.2 GB once and uses them for all 512 tokens
- Decode reads all 51.2 GB again for every single token

The number that decides it: FLOPs done per byte read from memory.

- H100's balance point: 989 TFLOP/s ÷ 3.35 TB/s = \~295 FLOPs per byte
- Prefill: \~490 FLOPs per byte, above it, so the Tensor Cores are the limit
- Decode: \~1 FLOP per byte, far below it, so memory is the limit

So the answer to Post 1's question: no, one decode token doesn't come close to using those 989 TFLOP/s.

Even at the full 3.35 TB/s, a decode step can't go faster than 15.3 ms. The GPU mostly waits for weights to arrive.

**Next post:** what if 32 users decode at the same time? The weights get read once for all of them.

- Decode floor: 51.24 GB / 3.35 TB/s = 15.3 ms per token.
